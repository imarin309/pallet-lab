## 0. エージェントへの依頼

ブラウザ向け調色パズルゲーム **Palette Lab** の v0.1 を実装してください。

最初に関連する2文書を通読し、**コンセプトを守り、仕様書を満たす形で、小さく実装・検証を繰り返してください**。この文書は実装方法と作業順序の指示であり、ゲームのルールを上書きするものではありません。

最終的に、ローカルで動作するゲームのソースコード、必要なテスト、README、検証結果を提出してください。コードを書くことだけで完了とせず、実際に実行可能なコマンドで検証してください。

### 文書の優先順位

1. **`palette-lab-concept.md`**：体験の目的・ゲームデザインの判断基準（Why）
2. **`palette-lab-game-spec.md`**：ゲームの挙動・画面・受け入れ条件（What）
3. **本書**：技術選定の細部・実装順・検証・納品内容（How）

矛盾を見つけた場合は、独断でゲームルールを変更せず、矛盾点と採用した暫定対応を記録してください。仕様書に **「未決定」** とある事項は、後述の検証を行ってから仮決定し、その根拠を `docs/implementation-decisions.md` に残してください。細部の決定待ちで、無関係な実装を止める必要はありません。

## 1. 実装するゲームの要約

- プレイヤーは **絵の具の基本12色**（赤・橙・黄・黄緑・緑・水色・青・紫・茶・黄土色・白・黒）を1滴ずつ混ぜ、お題の色に近づける。当初は5色だったが、v0.1 実装後に12色へ変更した。
- 1ステージ **最大8滴**。**直前の1滴を戻せるのは1回**。
- 1滴以上混ぜればいつでも完成を宣言できる。8滴に達したら追加不可だが完成は可能。
- 色の近さを **0〜100点** で採点し、星ランクと改善ヒントを表示する。
- **5つの固定ステージ**、同じステージへの再挑戦、次ステージへの進行を実装する。
- 正解色は、8滴以内の正解レシピを**プレイヤー側と同じ混色関数**に通して生成する。必ず100点を狙えるようにする。
- プレイ中は正解レシピやRGB値を公開しない。結果画面でも正解レシピは公開しない。
- オンライン機能や本格的な物理シミュレーションは初期版の対象外。

もっとも大切なのは、**「もう1滴足すか、ここで完成させるか」**という駆け引きと、「自分の判断で色が変わる」納得感です。

## 2. 技術スタックと制約

| 項目 | 指定 |
| --- | --- |
| ゲームフレームワーク | **Phaser**（公式テンプレートで利用可能な安定版） |
| 言語 | **TypeScript**（strict モード推奨） |
| 開発・ビルド | **Vite** |
| テスト | **Vitest** などの軽量な単体テストツール |
| 描画・入力 | 原則 Phaser の Scene / Game Objects / Input / Tween |
| UI | Phaser中心。ブラウザ由来のアクセシビリティ等で必要な場合のみHTML/CSSを併用 |
| 配信 | 静的ホスティング（Cloudflare Pages 等）を想定 |
| 不要 | React、Vue、バックエンド、DB、ログイン、外部画像アセット |

- Phaser の**実際に導入したバージョン**に対応する公式APIを使うこと。古い記事のコードをそのまま流用しない。
- `npm create @phaserjs/game@latest palette-lab` を初期構築の候補とし、**Vite + TypeScript、UIフレームワークなし**の構成を選ぶ。すでにリポジトリに実装や設定がある場合は、上書きせず内容を確認してから適用する。
- 依存バージョンは `package-lock.json` などのロックファイルで固定する。
- TypeScriptのゲームロジックは可能な限り Phaser に依存させず、単体テスト可能にする。
- 不必要なフレームワーク、状態管理ライブラリ、DIコンテナ、汎用ゲーム基盤を導入しない。

参考：Phaser公式セットアップ https://phaser.io/tutorials/create-game-app

## 4. 設計上の境界

### 4.1 ドメインロジック（Phaserに依存しない）

- `paintMixing`：塗料IDと滴数（または履歴）からRGB色を得る純粋関数。
- `scoring`：目標色と完成色から、整数スコア・ランク・判定可能なヒントを返す純粋関数。
- `gameRules`：滴の追加、最後の1滴の取り消し、完成可能判定を管理する。副作用を持たせない。
- `stages`：レシピとお題名を持つ。目標RGBは**同じ** `paintMixing` から算出する。

概念上の型は次のようなものを想定する。詳細は実装時に調整してよい。

```ts
type Pigment =
  | 'red'
  | 'orange'
  | 'yellow'
  | 'yellowGreen'
  | 'green'
  | 'lightBlue'
  | 'blue'
  | 'purple'
  | 'brown'
  | 'yellowOchre'
  | 'white'
  | 'black';
type RgbColor = { r: number; g: number; b: number };
type MixHistory = Pigment[];

type Stage = {
  id: string;
  name: string;
  recipe: MixHistory; // 合計8滴以内
};

type RoundState = {
  history: MixHistory;
  undoAvailable: boolean;
  completed: boolean;
};
```

- 滴の追加順を履歴として保持することで、「最後の1滴を取り消す」を正しく実現する。
- 色の計算結果は**滴数・比率に依存し、追加順には依存しない**ものとする。同じ内訳なら同じ色になる。
- 画面演出中も確定したゲーム状態と表示を区別し、演出の連打や遷移で二重入力されないようにする。

### 4.2 Sceneの責務

- `TitleScene`：タイトル・ルールの短い説明・スタート操作。
- `GameScene`：お題表示、塗料の選択、現在色表示、滴数・取り消し、完成操作、滴演出。
- `ResultScene`：色の比較、スコア・ランク・改善ヒント、同ステージ再挑戦・次ステージ遷移。

Scene間で受け渡すデータは明示的にし、グローバルな可変状態に過度に依存しない。結果の表示に必要な目標色、完成色、スコア、ステージ番号などを確実に引き継ぐ。

## 5. 未決定事項の進め方（重要）

ゲーム仕様書の未決定事項を、エージェントが根拠なしに「仕様確定」しないこと。以下の**検証 → 仮決定 → 記録**の順に進める。

### 5.1 混色アルゴリズム

最初に独立した小さな試作品で、**RGB加重平均**と、**絵の具らしい振る舞いを目指した簡易混色案**を比較する。

検証する組み合わせの例：

- 青＋黄 → 緑方向に見えるか
- 赤＋黄 → オレンジ方向に見えるか
- 白を追加 → 明るく、淡くなる傾向か
- 黒を追加 → 暗くなる傾向か
- 同じ滴の構成を違う順番で追加 → 最終色が一致するか
- 少量の1滴追加で、予測可能な変化になるか

**RGB加重平均を「実際の塗料を再現している」と説明しない。** 簡易案も実測の顔料シミュレーションと混同しないこと。必要なら色見本を簡単な検証ページや画像として並べ、色合いを目で比較できるようにする。

厳密な再現性より、**直感・決定論・十分な色の広がり・実装のわかりやすさ**を優先して v0.1 の方式を仮採用する。実装上は差し替え可能な境界を保ち、採用理由と限界を記録する。

### 5.2 採点方法

最低限、完全一致が100点、色差が大きいほど低得点、0〜100の整数範囲になること。

- RGB距離と、知覚差に配慮した方法（例：Lab空間の距離）の実装・テスト容易性を比較する。
- 色差からスコアへの変換に用いる係数や閾値は1か所にまとめ、比較可能なテストケースを作る。
- 近い色のわずかな違いが極端に減点されないか、明らかに違う色が高得点にならないか確認する。
- ヒントは確実に判定できる内容に限定し、根拠のない「赤を足すべき」などの処方は表示しない。

### 5.3 ステージと記録保存

- 選んだ混色方式で、**5ステージ分の8滴以内のレシピ**を作る。初級→中級→上級の変化が見えるようにする。
- 各ステージの正解レシピを入力したとき100点が出ることを自動テストする。
- 最高得点はまず**セッション中のみの保持**を暫定採用とする。リロード後の永続化は v0.1 の必須条件ではない。将来の `localStorage` 対応を容易にするが、先回り実装は不要。
- 仮決定した5レシピ、スコア方式、ヒント条件、記録方式は `docs/implementation-decisions.md` に残す。プレイテスト後に見直せるようにする。

## 6. 実装順序（各段階で動く状態を保つ）

### Phase 0 — 環境構築と仕様確認

1. 3文書を読み、要件を受け入れ条件のチェックリストに落とす。
2. 既存リポジトリを確認し、なければ公式テンプレートから Phaser + TypeScript + Vite を構築する。
3. `npm install`、`npm run dev`、`npm run build` の実行を確認する。
4. 型チェック（例：`npm run typecheck`）とユニットテスト（例：`npm run test`）のスクリプトを整える。
5. 公式テンプレートの不要なデモ画面・素材を最小限まで整理する。

**完了条件：** 空に近い Palette Lab のタイトル画面がブラウザで表示され、ビルドできる。

### Phase 1 — ゲームロジック（最優先）

1. 色・塗料・履歴・ステージの型を用意する。
2. 混色候補の比較試作を作成し、v0.1 の暫定方式を決める。
3. 滴の追加・8滴制限・1回だけの取り消し・完成可否を実装する。
4. 採点・ランク・改善ヒントの計算を実装する。
5. 5ステージを定義し、同じ計算でお題色を生成する。
6. 混色・ルール・採点の単体テストを追加する。

**完了条件：** Phaserの画面を使わず、ドメインロジックがテストで確認できる。

### Phase 2 — 最小限のプレイ可能版

1. `TitleScene` から `GameScene` に入れるようにする。
2. `GameScene` に目標色・現在色・12色のボタン・残り滴数・取り消し・完成を配置する。
3. 入力とロジックを接続し、即時の色更新を行う。**この段階では演出不要。**
4. `ResultScene` に完成色・目標色・スコア・ランク・ヒントを表示する。
5. 再挑戦・次のステージ・5ステージ終了の動線を完成させる。

**完了条件：** 演出がなくても、5ステージを最初から最後まで遊べる。

### Phase 3 — Phaserらしい演出

1. 1滴の追加時に、パレットへ滴が落ちる小さなアニメーションを入れる。
2. 色の切り替えを短いTween等で自然に見せる。
3. 結果スコアをアニメーションで表示する。
4. 演出中の連打、連続Scene遷移、処理の重複を防ぐ。

**完了条件：** 演出が追加されても、入力と結果の整合性が崩れない。

### Phase 4 — モバイル・品質確認

1. 小さい画面でも目標色と現在色を比較できるようにする。
2. Phaserのスケール設定、カメラ座標、ボタン位置を確認し、タッチ操作でも使えるようにする。
3. 画面サイズ変更、縦長画面、スマホでのタップ連打を確認する。
4. 型チェック、テスト、ビルド、手動プレイテストを実施する。
5. 不具合を修正し、READMEと実装判断記録を更新する。

**完了条件：** PC・スマホ双方で、主要なルールを破綻なく最後まで遊べる。

## 7. UIと演出の実装指針

- タイトルやボタンより、**目標色と現在色の比較しやすさ**を優先する。
- 比較する2つの色領域は同面積・同条件の背景で表示する。色は**演出による陰影がかかっていない面**でも比較できるようにする。
- 初期状態（0滴）は「未調色」とし、完成ボタンは無効化する。
- ボタンは塗料の色だけで区別させず、**「赤」「青」などの文字**を併記する。
- 入力できない操作（8滴到達後の追加、取り消し使用後の取り消し、採点後の操作）は見た目と処理の両方で防ぐ。
- Phaserでシンプルな図形を描画し、背景素材の制作は不要とする。
- 効果音、派手なパーティクル、詳細設定画面、チュートリアルの作り込みは不要。
- Canvas上の文字は環境によってフォントが異なるため、日本語表示と可読性を確認する。
- 色の変化を見るゲームなので、コントラストの低い文字や過度な画面演出を避ける。

## 8. テスト・検証の具体例

### 自動テスト（必須）

**混色**

- 入力が同じなら結果が同じ（決定論）。
- 同じ内訳なら追加順を入れ替えても色が変わらない。
- 出力RGBが常に有効範囲の有限値になる。
- 1色のみ、複数色、白・黒を含む調色を処理できる。
- 全5ステージのレシピが8滴以内で、同じ関数から目標色を算出できる。

**ゲームルール**

- 0滴の状態では完成できない。
- 8滴を超えて追加できない。
- 1滴戻すと直前の色が履歴から削除され、残り滴数が戻る。
- 取り消し権は1回だけ消費され、二度目の取り消しができない。
- 取り消し後に再び追加できる。
- 完成後の追加や取り消しを受け付けない。
- ステージ再挑戦時に履歴と取り消し権が初期化される。

**採点**

- 完全一致で100点。
- 点数は常に0〜100の整数。
- 色差の大小と点数の大小が矛盾しないことを、同じ尺度のテストケースで確認する。
- ランク境界（59/60、74/75、89/90、100点）が仕様書と一致する。
- すべてのステージで正解レシピを入力すると100点になる。

### 手動テスト（必須）

- スタート → 調色 → 完成 → 結果 → 再挑戦／次ステージまでの一連の操作。
- マウスとタッチで、1回の押下につき1滴追加されること。
- 8滴到達時と取り消し後に操作表示が正しいこと。
- 色が変わる演出と最終RGB表示が一致すること。
- PCの通常画面、スマホ縦長画面、画面リサイズ時に操作できること。
- 5ステージ終了後に意図した画面へ戻れること。

可能ならブラウザの自動操作で主要な画面遷移を確認する。ただしテスト環境の準備が大がかりになる場合、v0.1では手動操作とユニットテストを優先する。

## 10. 実装で避けること

- コンセプトにないルール（制限時間、課金要素、ランダムな失敗判定など）を増やすこと。
- 仕様にない12滴制限、無制限取り消し、正解レシピの自動公開を採用すること。
- お題の色を手書きのRGB定数で定義し、プレイヤーには到達できない色を出題すること。
- 表示されるアニメーションの色を採点する色と食い違わせること。
- Phaserに強く依存した計算コードを作り、ロジックをテスト不能にすること。
- すべての場面にゲームループ処理を置くこと。必要なタイミングにイベント駆動で更新すればよい。
- テストに失敗しているのに「完了」と報告すること。
- 本格的な顔料再現や豪華な演出に時間をかけ、基本ループが未完成になること。

## 12. 作業終了時の報告形式

実装を終了したら、以下の内容を短く報告してください。

1. **実装したもの**：動く範囲、対応ステージ、演出。
2. **技術構成**：実際のPhaser / TypeScript / Viteのバージョン。
3. **検証結果**：実行したコマンドと成功／失敗、手動検証の範囲。
4. **決めたこと**：混色、採点、ステージ、記録方式の仮決定。
